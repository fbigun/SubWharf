## 0. 一句话结论

单请求 CPU 成本的主导项不是「解析逻辑」，而是三处结构问题：

1. `src/auth.ts:34` 的 base64 解码用 `Uint8Array.from(atob(s), c => c.charCodeAt(0))`，**每字节一次回调**，解 140KB 花 8.5ms；
2. `src/subs.ts:430` 的 `uniqueNames` 在「清洗后同名」时是 **O(n²)**，400 个香港节点花 12.2ms；
3. `src/subs.ts:455` 的 `collectNodes` **逐订阅串行** await，8 订阅 16 跳 KV 串成一条链。

这三条都不是「微优化」，是能在免费版 10ms CPU 预算里占掉 100%+ 的结构性成本。

夹具规模说明：

- 解析：500 节点（明文 URI 105KB / base64 141KB），贴近常见机场量级
- Clash YAML：300 节点（受限解析器上限 `CLASH_MAX_NODES=300`）
- 输出：300 / 500 节点
- 采集：1 / 4 / 8 订阅，200~1600 节点

### 节点名画像：两种必须分开测的情况

`cleanNodeName` 会把 `🇭🇰 香港 01`、`🇭🇰 香港 02` 全部清洗成「香港」，于是撞上 `uniqueNames`。真实机场两者都常见：

- `collide`：`🇭🇰 香港 01/02/…` → 清洗后同名 → 走 `uniqueNames` 改名
- `distinct`：`Relay-001/002/…` → 未识别地区，保留原名 → 天然唯一

把两者平均会同时掩盖两个问题，所以下面全部拆开报。

## 2. CPU 侧基线

### 2.1 编解码（`src/auth.ts`）

`### counterfactual · base64 解码`

| case | p50µs |
|---|---|
| `b64ToBytes` 现实现（`Uint8Array.from` 回调），140KB | 8519 |
| `b64ToBytes` 反事实（分块下标写回） | 242 |

| case | p50µs |
|---|---|
| `bytesToB64` 现实现（逐字节字符串拼接），105KB | 1837 |
| `bytesToB64` 反事实（分块 `String.fromCharCode.apply`） | 473 |

**机制**：现实现对每个字节做一次 JS 函数调用（解码）或一次字符串 `+=`（编码）。分块版把逐字节操作换成引擎内建批量操作（`apply` 展开 + 连续下标写回），调用次数从 N 降到 N/8192。

**这是整份报告里最大的一笔**：单个函数就在 10ms 预算里拿走 8.5ms。

### 2.2 解析

| case | p50µs | 输入 |
|---|---|---|
| `parseUriList` 500 明文 | 2969 | 105422B |
| `parseSubscription` base64 500（默认抓取形态） | 11769 | 140564B |
| └ 其中 base64 解码一段 | 8581 | — |
| `parseClashYaml` 300 节点 | 3796 | 135458B |
| `parseClashYaml` 300 节点 + 400 行前导 rules | 3900 | 152955B |
| `parseSingboxJson` 500 outbounds | 822 | 254826B |

规模敏感性（明文 / base64，µs）：

| 节点数 | 明文 URI | base64 | 线性外推校验 |
|---|---|---|---|
| 50 | 297 | 1035 | 1.00× |
| 100 | 574 | 2264 | 1.09× |
| 200 | 1145 | 4467 | 1.08× |
| 300 | 1713 | 6765 | 1.09× |
| 500 | 2886 | 11188 | 1.08× |

**读法**：

- base64 路径比明文路径贵 4.0×，多出来的部分 97% 是解码（8581 解码 vs 2969 整条明文解析链），解析逻辑本身两者相同。
- 所以「优化解析器」对该形态几乎无意义；要动的是 `b64ToBytes`。
- Clash 解析器的成本与**前导行数无关**（3796 vs 3900）：它先定位 `proxies:` 再单遍扫，前导 400 行 rules 被跳过的成本在噪声内。这一栏说明现有受限解析器设计是对的。
- Clash 三栏（3796/3900µs）比明文 URI 路径（2969µs）贵约 30%：受限解析器要逐行正则 + 递归下降建树，而 URI 路径只是一行一个 `indexOf`。这与设计预期一致——Clash 形态只在个别机场作为兜底。

### 2.3 节点名清洗

| case | p50µs |
|---|---|
| `cleanNodeName` ×400 节点（一次请求级） | 769 |
| 命中城市别名（London / 东京 / 法兰克福） | 3.31 |
| 命中中文地区（香港 / 日本） | 1.50 |
| 命中英文缩写（`US-09`） | 1.64 |
| 命中英文全称（`Bosnia and Herzegovina`） | 1.37 |
| 未识别地区（直接返回原名） | 0.15 |
| 长名 + 多标识（最坏情况） | 3.51 |

**读法**：单节点 1.4~3.5µs，400 节点约 0.77ms。不是热点，但也不是零。别名档最贵（3.3µs）——`rename.ts:253` 把 20+ 条别名合成一条带命名捕获组的大正则，命中时引擎仍要试遍前面的分支，故比中文/英文档贵一倍。

**结论**：这一栏**不需要优化**。在当前量级（0.8ms/400 节点）对预算影响可忽略，改它属于「为零收益引入回归风险」。

### 2.4 采集汇总（去重 + 唯一命名）

I/O 置零（零延迟 KV 桩），测纯 CPU：

| case | p50µs |
|---|---|
| 名字清洗后同名 · 200 节点单订阅 | 3667 |
| 名字清洗后同名 · 400 节点单订阅 | 14637 |
| 名字清洗后同名 · 800 节点单订阅 | 58338 |
| 名字天然唯一 · 200 节点单订阅 | 632 |
| 名字天然唯一 · 400 节点单订阅 | 1280 |
| 名字天然唯一 · 800 节点单订阅 | 2615 |
| 8 订阅 / 800 节点，collide 画像 | 9267 |
| 400 节点 + 链接正则过滤 | 190 |

**uniqueNames 增长阶（collide 画像）**：

- 200→400 节点：耗时 ×3.99
- 400→800 节点：耗时 ×3.99
- 归一化增长因子：2.00 / 1.99（1.00 = 线性，2.00 = 平方）

**机制**：`subs.ts:437-439`

```ts
let i = 2;
while (used.has(`${n.name} #${i}`)) i++;
```

第 k 个同名节点要从 `#2` 数到 `#k`，每个候选都是一次模板字符串拼接 + 一次 Set 查询。合计 Σk = O(n²)。

**对照**：同样 400 节点，distinct 画像 1280µs，collide 画像 14637µs——**11.4× 差**，全部来自这一处。这不是理论推演，是实测阶数。

反事实（`counterfactual.bench.ts`，Map 记住下一个可用序号，O(n) 均摊）：

| 同名节点数 | 现实现 | 反事实 | 倍数 |
|---|---|---|---|
| 200 | 2576 | 43 | 59× |
| 400 | 11993 | 94 | 127× |
| 800 | 53057 | 195 | 272× |

输出逐项一致（含 `#2`、`#3` 分配顺序），见该用例断言。

### 2.5 输出序列化

| case | p50µs |
|---|---|
| `renderClash` 300 节点（rules=none） | 748 |
| `renderClash` 300 节点（rules=cn） | 698 |
| `renderSingbox` 300 节点（rules=none） | 573 |
| `renderSingbox` 300 节点（rules=cn） | 581 |
| `renderUri` 300 节点 | 801 |
| `renderBase64` 300 节点 | 1733 |
| `renderClash` 500 节点 | 1084 |
| `renderSingbox` 500 节点 | 881 |
| `renderUri` 500 节点 | 1246 |
| `renderBase64` 500 节点 | 3050 |
| `bytesToB64`（`renderBase64` 的编码步）×500 节点 | 1381 |

输出体积（300 节点）：

| 格式 | 字节 |
|---|---|
| Clash YAML | 90660 |
| sing-box（缩进 2） | 138229 |
| sing-box（压缩） | 89536 |
| URI | 65070 |
| base64 | 86760 |

**读法**：

- `renderBase64` ≈ `renderUri` + `bytesToB64`（1733 ≈ 801 + 1381，两项都是 p50，重叠部分是 `renderUri` 内部的一次编码）。所以**修好 `bytesToB64` 自动带走 `renderBase64` 的一半成本**。
- sing-box 缩进输出 138KB，压缩后 89KB——**省 35% 体积、35% 传输字节**，代价是客户端可读性（用户拿去看的话就值不回）。
- `renderClash (rules=none)` 比 `rules=cn` 慢 50µs（748 vs 698）：差异只有两行固定文本，属噪声，不要解读。

### 2.6 端到端请求（真实 `src/index.ts`）

桩 KV 零延迟，直接调 `worker.fetch()`，量 `/s/{token}` 一次的计算成本：

| 场景 | clash | singbox | base64 | uri |
|---|---|---|---|---|
| 300 节点 · 名字唯一 | 3353 | 2848 | 3974 | 1719 |
| 300 节点 · 同名清洗 | 5707 | 6905 | 6826 | 5006 |
| 500 节点 · 名字唯一 | 4327 | 5657 | 5201 | 2622 |
| 500 节点 · 同名清洗 | 13176 | 15147 | 14421 | 11818 |
| 800 节点 · 同名清洗 | 18154 | 18785 | 20364 | 16016 |

（单位 µs；预算 10000µs）

**20 个组合里 8 个超预算，全部落在「同名清洗 + ≥500 节点」区域**，超幅 18%~104%。

拆解 500 节点同名清洗的 13.2ms（clash）：

| 环节 | µs | 占比 |
|---|---|---|
| 采集（`collectNodes`，含 `uniqueNames`） | ~9500 | 72% |
| 序列化（`renderClash`） | ~1084 | 8% |
| `Response` 构造 + body 物化 | 余下 | — |

**结论**：把 `uniqueNames` 修好后，这一格从 13.2ms 掉到约 5ms 量级（采集段回到 distinct 画像的 1.3ms 量级）。

## 3. I/O 侧基线

### 3.1 KV 往返次数（确定值，与延迟无关）

| 场景 | get | list | 合计往返 |
|---|---|---|---|
| `collectNodes`：8 订阅 / 400 节点，不含自建 | 16 | 0 | **16** |
| `collectNodes`：8 订阅 + 5 自建节点 | 21 | 1 | **22** |
| `collectPool`：8 订阅 + 5 自建节点 | 21 | 2 | **23** |
| `/s/{token}` 读取段：`getLink` + `collectNodes`（8 订阅） | 17 | 0 | **17** |
| 单次 `getSub`（对照） | 1 | 0 | **1** |

**读法**：

- 8 订阅 = 16 次 = 8×(sub + snap)，**全串行**（`subs.ts:455-467` 的 for-await）。
- 自建节点多出 6 次 = `list('node:')` + 5 次 get（`subs.ts:68-76` 的 `listByPrefix` 逐键 get）。
- `/s/{token}` 每次客户端拉取重跑一遍，**无请求级 memo**。
- 配额账：10 万读/天 ÷ 17 次/请求 ≈ **5882 次 /s/ 请求/天**就吃满 KV 读配额（还没算管理面与 cron）。这只是「配额余量」结论，实际个人用量远低于此，但它是硬上限。

### 3.2 串行墙钟（桩延迟 3ms/跳，假设值）

| case | ms |
|---|---|
| KV get ×1（对照） | 3.08 |
| `collectNodes` 8 订阅 / 400 节点 · 名字唯一 | 50.98 |
| `collectNodes` 8 订阅 / 400 节点 · 同名清洗 | 52.89 |
| `collectNodes` 8 订阅 + 5 自建 · 名字唯一 | 70.35 |
| `/s/{token}` 读取段 · 名字唯一 | 53.81 |
| `collectPool` 8 订阅 + 5 自建 · 名字唯一 | 72.80 |

### 3.3 串行 vs 并发（结构代价）

| case | ms |
|---|---|
| 现有实现：8×(sub,snap) 串行 | 50.51 |
| 反事实：同一批读取 `Promise.all` 并发 | 3.20 |
| 反事实：按 6 路分批并发（贴合单请求 6 连接上限） | 9.26 |

- 串行 50.5ms vs 全并发 3.2ms：**15.8× 差**，即 16 跳被摊成 1 跳。
- 6 路分批 9.3ms 是**现实可取的**下限（README「六」：单请求最多 6 个并发连接）。
- `[unverified]` 真实 KV 单跳延迟分布、6 连接下的排队行为——本机无法测。
- **重要**：纯 I/O 等待不计入 CPU 时间，所以并发化对 10ms CPU 预算**无直接收益**，收益在墙钟（客户端首字节）。这两件事不能混着说。

## 4. 与免费版硬约束的对账

| 约束 | 值 | 现状 | 结论 |
|---|---|---|---|
| CPU / 请求 | 10ms | 500 节点同名清洗 11.8~15.1ms | **超**，主因 `uniqueNames` + `b64ToBytes` |
| CPU / 请求 | 10ms | 300 节点名字唯一 1.7~4.0ms | 通过，余量充足 |
| KV 读 / 天 | 100000 | 17 次/`/s/` 请求 | 约 5882 次/天到顶；需请求级 memo |
| KV 写 / 天 | 1000 | 快照写 + 缓存写，约 20/天量级 | 通过 |
| 子请求 / 次 | 50 | 抓 N 订阅（N<<50） | 通过 |
| 并发连接 / 请求 | 6 | 现为 1（串行） | 未用满，是可用的优化空间 |
| isolate 内存 | 128MB | 单请求峰值未测 | `[unverified]`，见 02 篇 |

## 5. 明确未验证的项（`[unverified]`）

以下结论**不能**从本文数字直接得出，必须在 workerd / 生产下确认：

1. **绝对值能否外推**：node 的 JIT、GC、内联策略与 workerd（V8 + Spectre 缓解）不同。02 篇给了实测对照，但仍不等于生产。
2. **Cloudflare 的 CPU 时间是否含 GC**：若含，「500 节点同名清洗」在生产会更容易触发 10ms 限流；若不含，实际余量更大。
3. **真实 KV 单跳延迟**：本文的 3ms 是 README 假设值。真实分布须 `wrangler tail` 观测。
4. **6 连接上限下的排队行为**：桩里并发 6 路是理想的，真实 KV 是否按连接数排队未知。
5. **isolate 内存峰值**：128MB 限制下单请求大输出（如 800 节点 sing-box 缩进 380KB）是否安全，需在 workerd 里跑大 payload。
6. **cron 场景的 CPU 上限**：Cron Trigger 的 CPU 预算与 HTTP 请求是否一致，README 未写死，须查平台文档或实测。
